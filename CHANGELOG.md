# Changelog

All notable changes to this template are logged here, newest first. Each entry maps to a merged pull request; the `#nn` reference links to the PR on GitHub. For full diffs, see the git history. Changelog-maintenance PRs (pure backfills such as #82, #100, #205, #222) and clone-local, non-template-facing decisions (the #184–#199 era) do not receive entries of their own; the authoritative exemption list and its categories live beside Check 12 in `Vault/Scripts/validate.sh`. An entry belongs on its own PR's branch, added after the PR number exists but before the squash-merge — never opened as a separate PR once the code PR has already merged.

This log tracks the **template itself** — structural changes clones inherit on a fresh pull. It does not track work done inside an individual clone (that lives in `Vault/Memory/`, which is per-clone and largely git-ignored).

## 2026-09-04

- fix(tools): hardens `Vault/Scripts/tool-check.sh`'s `--apply` path against three gaps. `lock_epoch` now strips a trailing CR and falls back to `0` on any non-digit content (`case ... *[!0-9]*`, the same idiom as `read-guard.sh`/`capture-log.sh`/`.claude/statusline.sh`) instead of guarding emptiness only, so a garbled stale lock now reads as ancient and is taken over rather than aborting the `$(( ))` arithmetic under `set -u`; the comparison itself now forces base 10 (`10#$lock_epoch`, the idiom plan 115 already put in `update-check.sh`), because the `case` guard admits leading-zero digit strings and bash's default base guessing reads those as octal — an un-forced `epoch=0129` or `08` still aborted the arithmetic, `apply_plannotator` returned 1 with nothing logged, and the SessionStart hook reported success on a run that never ran. The poisoned-staging path — a same-tag `.part` that hashes wrong but isn't a genuine partial (disk corruption, a Drive truncation-then-refill) — now retries from byte zero only on the curl exits that actually implicate the staging file itself: 22 (HTTP error under `-f`, the 416-on-resume case), 33 (server refused the range) and 36 (local file longer than the source). Every other failure — timeout or stall (28), the size cap (63), DNS, TLS, or a connection reset mid-transfer — still keeps the partial for tomorrow's resume exactly as `main` always did; retrying those inside the same 180s budget a 154 MB asset cannot clear on a slow link would have thrown away genuine progress every day. The two retry sites collapse into a single exit-4 message that now names the curl exit code and tells the truth about what's on disk — "partial file kept … for resume" when `-f -o`'s lazy-opened output file exists, "nothing staged; it will try again tomorrow" when a pre-body failure (measured: exit 1, exit 37) left none. The header's exit-code table row for exit 4 is qualified to match, now reading "partial staging kept for resume when one exists". This deviates from the plan's unconditional delete-and-retry on first failure (Senior Adviser ruling, Checkpoint A, revised after a 28-case QA adversarial table flagged the original narrower keep-list): the live Windows asset measures 154,476,032 bytes, needing roughly 860 KB/s to clear the 180s cap, so an unconditional (or over-broad) delete would discard genuine resume progress every day and the download could never complete. All three curl calls (`fetch()`, the resume attempt, the retry attempt) now carry `--proto '=https' --proto-redir '=https'`, closing curl's default allowance of a plain-http redirect; the two download attempts gain `--max-filesize 536870912` (the plan specified 200 MB, raised here because the Windows asset alone is already ~154 MB) and `fetch()` gains `--max-filesize 1048576` (the release JSON runs ~57 KB, its `.sha256` sibling 92 bytes) — noted honestly rather than as a hard guarantee: curl only enforces `--max-filesize` mid-transfer from 8.4.0 onward, is advisory below that when the origin sends no `Content-Length`, and under `-C -` bounds the bytes transferred in that attempt, not the file's total size. The header comment no longer claims "no external tool makes the accept/reject decision" — it now says the comparison logic runs in this script, but the published digest comes from the same GitHub origin as the asset, proving transfer integrity rather than publisher intent. Deliberately untouched: the post-transfer hash check, `.tag` mismatch handling, install/placement logic, the `PLANNOTATOR_BIN` path-management guard, and release-version pinning (still deliberately unpinned per `Resources/Onboarding/SETUP.md`'s accepted-risk note).
