Rate Limiting in the SQ API Gateway

TL;DR

The SQ API Gateway applies a token bucket rate limiter at the edge — 100 requests per 10-second window per API key. Requests that exceed the limit receive HTTP 429 with a Retry-After header. Implement exponential back-off in every client. Do not retry immediately on 429 — it compounds the problem.

Overview

Rate limiting prevents any single API key from monopolising gateway capacity. Without it, a burst of automated requests from one integration starves other callers and can cascade into upstream service failures.

The SQ API Gateway uses a token bucket algorithm. Each API key has its own bucket that refills at a constant rate. Requests consume tokens. When the bucket empties, requests are rejected until it refills.

Deep dive: why token bucket over fixed-window counting?

Fixed-window counters reset at clock boundaries. A client that fires 100 requests at 09:59:59 and another 100 at 10:00:01 effectively sends 200 requests in 2 seconds — the window boundary creates a burst seam. Token bucket avoids this: tokens refill continuously at 10/second, so a burst consumes the reserve but the refill rate stays constant regardless of clock alignment.

The downside is that token bucket allows short bursts above the nominal rate (up to the bucket capacity). The SQ gateway caps bucket capacity at 100 tokens, so the maximum instantaneous burst is 100 requests — the full 10-second allowance consumed in under a second.

How it works

Each incoming request is keyed on the X-Api-Key header. The rate limiter checks the token count for that key in Redis, decrements by 1 if tokens are available, or rejects with 429 if the bucket is empty.

Sequence: token bucket check per request

Simplified Redis Lua script executed atomically on each request:

-- rate_limit.lua
local key      = KEYS[1]          -- "rl:{api_key}"
local capacity = tonumber(ARGV[1]) -- 100
local refill   = tonumber(ARGV[2]) -- 10 tokens/second
local now      = tonumber(ARGV[3]) -- unix timestamp (ms)

local data     = redis.call("HMGET", key, "tokens", "last_refill")
local tokens   = tonumber(data[1]) or capacity
local last     = tonumber(data[2]) or now

-- Refill
local elapsed  = math.max(0, now - last)
tokens = math.min(capacity, tokens + elapsed / 1000 * refill)

if tokens < 1 then
  return 0   -- reject
end

tokens = tokens - 1
redis.call("HMSET", key, "tokens", tokens, "last_refill", now)
redis.call("PEXPIRE", key, 10000)
return 1     -- allow

Daily ceiling enforcement

The daily ceiling is a separate fixed counter keyed on rl:daily:{api_key}:{date}, incremented on every allowed request and expiring at midnight UTC. When the daily ceiling is reached, requests return 429 with a Retry-After value equal to seconds remaining until midnight. The token bucket and daily counter are checked in sequence — both must pass.

Handling 429 responses

Never retry immediately on 429

An immediate retry when the bucket is empty consumes a network round-trip, returns another 429, and — if you are in a tight loop — can trigger IP-level throttling at the load balancer. Always respect Retry-After or use exponential back-off with jitter.

The gateway sets three headers on every response to help clients self-regulate:

  • X-RateLimit-Limit — bucket capacity for this key
  • X-RateLimit-Remaining — tokens remaining after this request
  • Retry-After — seconds to wait before retrying (only on 429)

Implementation

The same back-off pattern applies across languages. Tab between implementations below.

// Exponential back-off with jitter — JavaScript (fetch)
const MAX_RETRIES = 5;

async function sqRequest(url, options, attempt = 0) {
  const res = await fetch(url, options);

  if (res.status === 429 && attempt < MAX_RETRIES) {
    const retryAfter = parseInt(res.headers.get('Retry-After') ?? '1', 10);
    const base  = retryAfter * 1000;
    const jitter = Math.random() * 500;
    const delay = Math.min(base * Math.pow(2, attempt) + jitter, 30_000);
    await new Promise(resolve => setTimeout(resolve, delay));
    return sqRequest(url, options, attempt + 1);
  }

  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json();
}
# Exponential back-off with jitter — Python (httpx)
import httpx, time, random

MAX_RETRIES = 5

def sq_request(url: str, headers: dict, attempt: int = 0) -> dict:
    res = httpx.get(url, headers=headers)

    if res.status_code == 429 and attempt < MAX_RETRIES:
        retry_after = int(res.headers.get("Retry-After", 1))
        base  = retry_after * (2 ** attempt)
        jitter = random.uniform(0, 0.5)
        time.sleep(min(base + jitter, 30))
        return sq_request(url, headers, attempt + 1)

    res.raise_for_status()
    return res.json()
#!/bin/sh
# Shell script with manual retry loop
# Note: 'Retry-After' header not parsed — uses fixed 5s back-off for demo
MAX=5
ATTEMPT=0

while [ $ATTEMPT -lt $MAX ]; do
  HTTP_CODE=$(curl -s -o /tmp/sq_resp.json -w "%{http_code}" \
    -H "X-Api-Key: $SQ_API_KEY" \
    "https://api.sampleclient.com/v1/orders")

  if [ "$HTTP_CODE" = "200" ]; then
    cat /tmp/sq_resp.json
    exit 0
  elif [ "$HTTP_CODE" = "429" ]; then
    ATTEMPT=$((ATTEMPT + 1))
    DELAY=$((5 * (2 ** (ATTEMPT - 1))))
    echo "Rate limited. Waiting ${DELAY}s (attempt $ATTEMPT)..." >&2
    sleep "$DELAY"
  else
    echo "Error: HTTP $HTTP_CODE" >&2
    exit 1
  fi
done

echo "Max retries reached" >&2
exit 1

Glossary

Token bucket
A rate-limiting algorithm where each caller has a "bucket" that holds up to a fixed number of tokens. Tokens are consumed by requests and refilled at a constant rate. When the bucket is empty, requests are rejected until tokens replenish. Allows short bursts up to the bucket capacity.
Exponential back-off
A retry strategy where the wait time between retries increases exponentially with each failed attempt — typically base * 2^attempt — usually with added random jitter. Prevents multiple clients from retrying simultaneously and worsening congestion.
Jitter
A small random value added to a retry delay. Without jitter, multiple clients that all received a 429 at the same moment would all retry at the same moment after their back-off interval — producing another burst. Jitter spreads retry timing and smooths load.
Dead-letter queue (DLQ)
A message queue that receives messages that could not be processed successfully after a defined number of retries. In the rate-limiting context, a DLQ stores failed API calls for later inspection and manual reprocessing rather than silently dropping them.
Rate-limit window
The time period over which requests are counted. A 10-second window means the gateway tracks all requests in any rolling 10-second span. Distinct from a fixed window, which resets on clock boundaries.

FAQ

Why do I get 429 even when I'm under 100 requests per 10 seconds?

Two possibilities: (a) your requests are bursty — 100 requests fired in 200ms exhausts the bucket even though the 10-second average is low; or (b) you are sharing an API key across multiple workers, and combined they exceed the bucket. Split your workers across separate API keys or add pre-emptive throttling (check X-RateLimit-Remaining and slow down as it approaches zero).

Does the daily ceiling reset at midnight UTC or local time?

UTC. The key rl:daily:{api_key}:{date} uses the UTC date as the date component and expires at the next UTC midnight. If your workload spikes at midnight local time in a UTC+10 timezone, you are hitting the window boundary at 10:00 UTC — plan accordingly.

Can I request a temporary rate-limit increase for a campaign launch?

Yes — contact SQ ops at least 5 business days before the launch date. Provide: expected peak requests/second, duration of the elevated period, and the API key(s) affected. Ad-hoc increases are available on Business and Enterprise tiers only. Standard tier must upgrade first.

Is the Redis token bucket state shared across gateway nodes?

Yes. All gateway nodes share a single Redis cluster (ElastiCache, two replicas). The Lua script runs atomically via EVAL, so the token count is consistent across nodes. There is a theoretical race window of <1ms per request — in practice this means the effective burst ceiling is capacity + (number of gateway nodes − 1) at peak, which is acceptable.

What happens if Redis is unavailable?

The gateway fails open by default — requests are allowed through without rate-limit checking. An alert fires within 30 seconds and the ops runbook calls for Redis recovery before the next major event window. This decision was made deliberately: a hard fail-closed would take down all API consumers, which is worse than a brief window of unthrottled traffic.
