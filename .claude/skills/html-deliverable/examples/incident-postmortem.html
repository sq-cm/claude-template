Root Cause Analysis

Root cause: A Cloudflare WAF rule deployed to production used a broad regular expression (.*[?&](id|token|key|session)=[A-Za-z0-9]{16,}.*) intended to block malicious checkout parameter injection. The regex matched Cloudflare's own Rocket Loader query string (__cf_chl_rt_tk=), which is appended to all page requests by Cloudflare. Because Rocket Loader tokens are 16+ alphanumeric characters matching the token capture group, every page request was blocked.

Contributing factor: The WAF rule was not validated against a staging environment before production deployment. The staging Cloudflare zone does not have Rocket Loader enabled, so the conflict would not have been detected even if staging had been used.

This is not a novel failure mode. Overly broad WAF rules are a known category of self-inflicted outage. The absence of a pre-deploy validation step (or a canary deployment window) was the controllable failure.

Five Whys

# Why? Answer
1 Why did the site go down? Cloudflare WAF returned 403 for all requests.
2 Why did WAF return 403 for all requests? Rule 14 matched Cloudflare Rocket Loader query strings present on every page request.
3 Why did Rule 14 match Rocket Loader strings? The regex was too broad — it matched any query parameter with a 16+ character alphanumeric value, not just malicious checkout parameters.
4 Why was the regex too broad? The rule was written and reviewed without testing against real production traffic patterns, including Cloudflare-injected parameters.
5 Why was it not tested against production traffic patterns? No WAF deployment checklist existed. There was no requirement to validate rules in a shadow/log-only mode before activating them.

What Went Well

Detection was systematic. The outage was detected via automated monitoring — not a client report. This is the intended behaviour.

Root cause was isolated in under 10 minutes. The Cloudflare Firewall Events log provided a clear trail directly to the offending rule. No guesswork was required.

Communication was clear and timely. Client was notified within 4 minutes of confirmation, received a plain-language summary, and an all-clear within 5 minutes of resolution.

What Went Poorly

No pre-deploy validation step. The WAF rule went live without any log-only validation period. This is the single controllable failure that caused the outage.

Staging zone does not mirror production. Even if a staging check had been in the process, it would not have caught this bug because Rocket Loader is not active on staging. Infrastructure parity is a known gap that has not been addressed.

14-minute detection lag on a Sunday P1. 14 minutes is acceptable but not ideal. Reducing polling to 1-minute intervals (Action 5) will close this gap for future incidents.
